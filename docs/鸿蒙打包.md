# 鸿蒙（HarmonyOS）打包说明

Flutter 客户端（`mobile/`）的鸿蒙适配。**只涉及 Flutter 客户端**，Go 服务端不变。

## 一句话结论

工程侧适配已完成，`mobile/ohos/` 可以直接用 DevEco Studio 打开；但本机没有鸿蒙工具链，
`.hap` 需要你装好 DevEco Studio + 鸿蒙版 Flutter 后执行 `./scripts/build-ohos.sh` 产出。

## 关键决策：用系统 RelationalStore 替代 sqlite3

`drift` 在其它平台走 `NativeDatabase`（`package:sqlite3` + FFI）。鸿蒙上这条路走不通，原因有两层：

1. `sqlite3` / `sqlite3_flutter_libs` 都没有 ohos 实现，社区也没有可用的 `sqlite3-ohos.dart` 仓库；
2. 更要命的是，鸿蒙版 Flutter 的 FFI 构建钩子会把 `targetOS` 伪装成 `linux`
   （见 `flutter_tools/lib/src/isolated/native_assets/targets.dart` 的 `OhosAssetTarget`），
   于是 `sqlite3` 会下载 **glibc 版** 预编译库打进 HAP —— 构建能过，运行期 `dlopen` 必失败。

所以改成：**RDB（`@kit.ArkData` 的 relationalStore，底层就是系统 SQLite）作为存储引擎，
drift 仍然负责 ORM 和查询构造**。业务代码一行没改。

```
业务代码（drift 生成表/查询）
        ↓
AppDatabase ← DelegatedDatabase ← OhosRdbDelegate   lib/data/db/ohos_rdb_database.dart
        ↓  MethodChannel 'caldav_free/rdb'
RdbBridge.ets（ArkTS）                              ohos/entry/src/main/ets/rdb/RdbBridge.ets
        ↓
系统 RelationalStore = SQLite（WAL、事务、索引）
```

平台分流只有一个入口 —— `local_database.dart` 的 `_openStore()`：
鸿蒙返回 `DelegatedDatabase(OhosRdbDelegate(...))`，其它平台仍旧 `_openFile(path)`。
`AppDatabase.memory()`（单测用）保持 `NativeDatabase.memory()` 不变。

## 已知缺口与待验证点

按优先级排：

1. **本地提醒不生效**（P1）。`flutter_local_notifications` 没有 ohos 实现，鸿蒙走
   `NoOpNotificationGateway`，任务提醒不会弹。补法是写一个 ArkTS 侧
   `reminderAgentManager` 桥，实现 `NotificationGateway` 接口后替换
   `createDefaultGateway()` 的返回值 —— 调度器和 UI 都不用改。
2. **ArkTS 通道 API 名称**。`MethodChannel` / `MethodCall` / `BinaryMessenger` 的
   引入路径按 ohos 插件惯例写的是
   `@ohos/flutter_ohos/src/main/ets/plugin/common/...`。首次编译若报找不到符号，
   按引擎实际导出路径改 import 即可，逻辑不用动。
3. **HTTP 明文**。登录页默认 `http://`，鸿蒙对明文 HTTP 的策略需在真机上确认；
   若被拦，需在 `module.json5` 补 `network_config`（或直接让用户填 HTTPS）。
4. **RDB 事务语义**。`beginTransaction()` / `commit()` / `rollBack()` 用的是 RDB 官方
   接口；嵌套事务用 `SAVEPOINT s<N>`。首次真机跑起来要先验「新建任务 + 批量同步」
   这两条写路径。
5. **性能**。每条 SQL 过一次通道，单条微秒级；批量写走 drift batch 已合并。
   若时间线/看板在大数据量下卡，再把热点查询下沉成 ArkTS 专用方法。

## 构建提速（实测数据）

用 `.hvigor/report/report-*.json` 里的任务级 duration 事件定位到瓶颈（单位纳秒），
优化前后同一台机器、同一个 debug 构建：

| 任务 | 优化前 | 优化后 | 说明 |
| --- | --- | --- | --- |
| `entry:default@CompileArkTS` | 242.4 s | 2.1 s | 关键路径，占整轮 70% |
| `entry:default@DoNativeStrip` | 96.5 s | 0.8 s | 和 ArkTS 并行，Debug 下没必要 |
| `init`（含 `ohpm install` 32.6 s） | 90.5 s | 摊薄到守护进程 | 只在首次付 |
| `entry:default@FlutterTask` | 4.1 s | 2.3 s | |
| **整轮** | **5 m 43 s** | **9.4 s** | 改一行 ets 后重新出包 |

配置依据全部在本机 hvigor 6.26.9 里核对过键名，不是照抄：

- `ohos/hvigor/hvigor-config.json5`
  - `execution.daemon / incremental / parallel`：字段见 `hvigor/res/hvigor-config-schema.json`
  - `execution.optimizationStrategy: "performance"`（可选值只有 `memory` / `performance`）
  - `hvigor.enableMemoryCache`、`hvigor.incremental.optimization`、`hvigor.task.schedule.optimization`
    —— 键名见 `hvigor/src/common/const/const.js`
  - `ohos.arkCompile.noEmitJs`、`ohos.processLib.optimization`、`ohos.obfuscationRules.optimization`
    —— 键名见 `hvigor-ohos-plugin/src/const/common-const.js`
- `ohos/entry/build-profile.json5`
  - `buildOptionSet[{name:"debug"}].nativeLib.debugSymbol.strip: false`
    —— 字段见 `hvigor-ohos-plugin/src/options/build/build-opt.d.ts` 的 `DebugSymbol`

没有采用的建议（原因写在后面，避免以后重复踩）：

- **`compressNativeLibs: false`**：它省的是打包压缩，不是 `DoNativeStrip`。本工程只有
  `libsqlite3.so` 一个原生库，且 strip 已经关掉，收益接近 0。Debug HAP 154 MB 主要是
  debug 版 `libflutter.so`，跟这个开关无关。
- **`.ohpmrc` 的 `enable_unified_lockfile` / `enable_boost_extraction_speed`**：本机
  ohpm 26.0.0.630 的包体里搜不到这两个键，无法确认生效，先不动。依赖安装的 32.6 s
  已经靠守护进程摊平了。
- **HSP → HAR**：本工程没有 HSP，不适用。

注意：`flutter build hap` 硬编码了 `--no-daemon`，走它拿不到守护进程收益。
日常改完 ets 用 `./scripts/build-ohos.sh --fast`，它直接调 `hvigorw --daemon`。

## 构建失败怎么定位（别再看 exit code 255）

`flutter build hap` 失败时只打印 `ProcessException: The command failed with exit code 255`，
真报错在 hvigor 自己的 debug 日志里：
`mobile/ohos/.hvigor/outputs/build-logs/build.log`（几百 KB、几百条 WARN、同一段错误连打三遍）。

```bash
cd mobile
./scripts/ohos-diag.sh --history   # 1 秒出结论：类型 + 错误列表（file:line）+ 每轮耗时与死因
./scripts/ohos-diag.sh -v          # 连 345 条 WARN 也看
```

`build-ohos.sh` 构建失败时会自动调它，不用手动翻日志。

定位慢的五个原因，以及已经做掉的优化：

| 原因 | 表现 | 处理 |
| --- | --- | --- |
| 报错被 flutter 吞掉 | 只知道 exit 255 | `ohos-diag.sh` 从 hvigor 日志还原 |
| 同一错误打印三遍、夹杂 345 条 WARN | 眼睛找不动 | 脚本按 `file:line` 去重 |
| 每轮都是全量构建 | `IS_FULL_BUILD=true`、`IS_DAEMON=false`，一轮 2~5 分钟 | 只是改 ets 用 `./scripts/build-ohos.sh --fast`（hvigor 守护进程 + 增量） |
| 环境类错误串行暴露 | `flutter-hvigor-plugin` 缺失 → 配置超限 → 网络 → 代码，一次只见一个 | `build-ohos.sh` 预先补 `ohos/node_modules/flutter-hvigor-plugin` 链接；`--check` 先体检 |
| 构建期下载原生库 | sqlite3 的 hook 去 github 拉 glibc 版 `libsqlite3`，超时 2.5 分钟 | 见下 |

若要彻底干掉原生库下载（鸿蒙侧已走 RDB，不需要它）：在 `mobile/pubspec.yaml` 根层加

```yaml
hooks:
  user_defines:
    sqlite3:
      source: system   # 不再下载预编译库；dlopen libsqlite3.so
```

注意这会同时影响 Android/iOS 的打包结果，改前先在另外两端各跑一次构建。

## 出问题怎么排查

| 现象 | 先看 |
| --- | --- |
| `exit code 255`，没有任何细节 | 真报错不在 flutter 输出里，跑 `./scripts/ohos-diag.sh` |
| `Cannot find module 'flutter-hvigor-plugin'` | `ohos/node_modules/flutter-hvigor-plugin` 符号链接缺失或指向失效，`build-ohos.sh` 会自动补建 |
| `COMPILE RESULT:FAIL` | `./scripts/ohos-diag.sh` 列出 ets 报错；改完用 `--fast` 增量重编 |
| `Unsupported platform: ohos` | 说明还在用 `NativeDatabase`，检查 `local_database.dart` 的 `_openStore()` 是否被改回 |
| 启动即 `RDB 尚未打开` | `EntryAbility.configureFlutterEngine` 里 `RdbBridge.attach` 没执行，或通道名不一致 |
| 数据每次启动都丢 | `filesDir` 通道没通，落到了 `systemTemp`（看 `appStorageDirectory()` 注释） |
| `hvigor: command not found` | DevEco Studio 未装或 `ohpm`/`hvigorw` 没进 PATH |
| 签名失败 | JDK 不是 17，或未在 DevEco 里登录华为账号 |

## 打包成功的判定标准（别看 exit code）

`flutter build hap` 在 hvigor 打包**之后**还会检查 `ohos/build-profile.json5` 里的 `app.signingConfigs`，为空就
`throwToolExit`，退出码非 0 —— 但此时 HAP 已经躺在 `ohos/entry/build/default/outputs/default/` 里了。
所以判断标准是 hvigor 日志的最后一行，不是 flutter 的退出码：

```bash
grep -E "BUILD (FAILED|SUCCESSFUL) in" mobile/ohos/.hvigor/outputs/build-logs/build.log | tail -1
ls -lh mobile/ohos/entry/build/default/outputs/default/*.hap
```

`build-ohos.sh` 已经按这个判定：hvigor 说 `BUILD SUCCESSFUL` 且产物存在 → 打印「打包本身成功」并退出 0，
只有日志里真是 `BUILD FAILED` 才去跑 `ohos-diag.sh` 并返回 1。

`entry-default-unsigned.hap` 是**未签名**包，`hdc install` 会被拒。签名只能在 DevEco Studio 图形界面里做一次：

1. DevEco Studio 打开 `mobile/ohos`（不要打开 `mobile`，否则不是鸿蒙工程）
2. File > Project Structure > Signing Configs
3. 勾选 **Automatically generate signature**，登录华为账号，等它生成 `.p12` / `.cer` / `.p7b`
4. 生成后会写回 `ohos/build-profile.json5` 的 `signingConfigs`，此后 `./scripts/build-ohos.sh` 直接出签名包

签名产物与 unsigned 包同目录，文件名是 `entry-default-signed.hap`，装机：

```bash
hdc install -r mobile/ohos/entry/build/default/outputs/default/entry-default-signed.hap
```

### RDB 桥接的一个坑（已修）

`ResultSet.getColumnName(i)` / `getColumnTypeSync(i)` 要求结果集**先定位到有效行**，否则抛
`ResultSet is empty or pointer index is out of bounds.`，表现为启动即「本地数据初始化失败」。
`RdbBridge.query` 现在用行无关的 `getColumnNames()` 取列名，列类型改为读到第一个非 NULL 值时再推断
（首行是 NULL 的整数列不会被误判成字符串），空结果集的类型给 `STRING` 占位。

## 原生通知验证结果（模拟器 / 未签名包）

两条链路要分开看，它们走的是完全不同的系统 API：

| 通道 | API | 模拟器未签名包 | 真机签名包 |
| --- | --- | --- | --- |
| 即时通知 | `notificationManager.publish` | ✅ 可用 | ✅ 可用 |
| 定时提醒 | `reminderAgentManager.publishReminder` | ❌ 配额为 0 | 需 AGC 开通「代理提醒」能力 |

### 即时通知：可用

`entry/src/main/ets/notify/NotifyBridge.ets` 的 `showNow` → `notificationManager.publish`，
模拟器上实测弹出了通知卡片（应用名「历记」）。设置页「发送测试通知」验证的就是这条。

### 定时提醒：未签名包配额被系统置 0

`publishReminder` 一律返回 `1700002 The number of reminders exceeds the limit`，
但 `getValidReminders()` 返回空数组 —— 也就是说「超限」不是因为堆了旧提醒。

系统侧日志（`hilog | grep ANS_REMINDER`）才是真相：

```
E Ans: VerifyCloudCapability failed. uid = ..., capability = reminder_capability.
W Ans: ReminderControl com.caldavfree.caldav_free, notification not allowed.
W ANS_REMINDER: The number of reminders exceeds the limit[0].
```

`limit[0]` 说明这个包的提醒配额是 **0**。原因是 `bm dump` 里
`appProvisionType: debug`、`appDistributionType: none` —— 未签名包没有 provisioning
profile，`reminder_capability` 为空（上面文章里「场景二」讲的就是这个）。

两个容易踩的细节：

- **必须排除参数问题**。用最小参数集（只有 `reminderType` / `dateTime` / `title` / `content`）
  重试仍是 `1700002`，就能确定与字段无关，别再逐项改字段。
- **触发时间不能太近**。留 10 秒会返回 `401 Parameter error`，留 60 秒才走到配额检查。
  排查时别被这个 `401` 带偏。

### 解决办法与当前降级

要真正用上系统级提醒，需要：AGC 开通「代理提醒」能力 → 重新生成 Profile →
DevEco 里改**手动签名**（自动签名不带管控能力）→ `module.json5` 声明
`ohos.permission.PUBLISH_AGENT_REMINDER`。设备需 HarmonyOS 6.0.0(20) 及以上。

在拿到签名之前，`OhosNotificationGateway` 做了降级：`schedule` 命中 `1700002` 时，
记 `nativeRemindersUnavailable = true`，改用 Dart `Timer` 到点调 `showNow`。
效果是「应用活着就一定会响」，进程被回收则不响；设置页副标题会显示
「系统提醒不可用，仅在应用运行时生效」，不让人误以为是系统级提醒。

验证记录（模拟器，11:24 那次）：

```
11:24:14.920  [NotifyBridge] schedule FAILED id=990004 err=code=1700002 ...
11:24:14.941  ohos reminder quota is 0, falling back to in-app timers
11:25:14.851  [NotifyBridge] published id=990004 title=定时提醒测试
```

刚好 60 秒后弹出，通知中心可见。设置页「测试定时提醒」就是这条链路的回归用例。

指到 `$DEVECO_SDK_HOME`。

镜像公开可直接拉（`ghcr.io`，无需 token；workflow 里仍带 `GITHUB_TOKEN` 以防限流），
下载约 2.7 GB、解压后 8.6 GB。**tag 就是 API 版本**，升 SDK 只改 `container.image` 这一行。

> 怎么确认 tag 存在：`docker manifest` 或
> `curl -H "Authorization: Bearer <token>" https://ghcr.io/v2/honjow/harmonyos-build-env/tags/list`
> 现有 tag：`6.1-api23`、`6.1-api24`、`26.0-api26`，以及带小版本的 `26.0.0.821` 等。

### 镜像里没有 Flutter，得自己 clone

官方 Flutter 没有 ohos target，必须用 gitcode 上的 `flutter_flutter` 分支。job 里按 tag 拉：

```yaml
env:
  FLUTTER_OH_REF: "3.47.7+ohos-0.0.1-pre"
  FLUTTER_OH_REPO: "https://gitcode.com/openharmony-tpc/flutter_flutter.git"
  FLUTTER_DIR: "/opt/flutter_flutter"
```

用 tag 而不是分支：分支会漂，tag 可复现。clone 用 `--depth 1`，约 1.1 GB（含
`bin/cache` 里 910 MB 的 Dart SDK 与引擎产物），所以整目录按 tag 缓存。

引擎产物由 flutter 首次运行时下载，鸿蒙那部分走华为 OBS：
`https://flutter-ohos.obs.cn-south-1.myhuaweicloud.com`（见 `flutter_tools/lib/src/cache.dart`
的 `ohosStorageBaseUrl`），托管 runner 可以访问。

### 实测（本机用同一镜像 + 同一份脚本跑通）

| 步骤 | 耗时 | 说明 |
|---|---|---|
| 校验容器工具链 | 1.4 s | 缺 git/curl/xz/java/ohpm/hvigorw 就直接报错 |
| 放宽 ohpm 重试 | 3.3 s | `retry_times=3`、`fetch_timeout=180s` |
| 准备 flutter + local.properties | 36.7 s（冷）/ 1.4 s（缓存命中） | 冷路径含 clone 与首次下载 Dart SDK、引擎产物 |
| 构建 HAP | 70.8 s | hvigor 内部 43.8 s |
| 归档 | 0.3 s | 29 MB，sha256 打印出来 |
| **合计** | **1 分 55 秒（冷）/ 约 77 秒（热）** | 不含镜像拉取 |

这台机器就在国内，clone 与华为 OBS 都很快；GitHub runner 上冷路径会慢一些，但仍是
分钟级。这与之前 `ErBWs/setup-ohos` 方案（10~20 分钟）不是一个数量级。

产物：**29 MB**，只有 `arm64-v8a` 一套 so —— 因为构建命令带
`--target-platform ohos-arm64`。里面是 `libflutter.so` 17.4 MB + `libapp.so` 8.2 MB（AOT）
+ `libsqlite3.so` 1.6 MB。没有 `kernel_blob.bin`，也没有 x86_64（模拟器才需要）。

### 四个不显眼但会炸的点

**0. 容器 job 的 step 可能跑在 `sh` 里。** 这是第一次在 GitHub 上真跑时才暴露的：
job 挂在第一个 step（`Verify container toolchain`）上，日志里什么都没打出来，注解只有一句
`Process completed with exit code 2`。原因是这一步第一行写了 `set -o pipefail`，而 dash 不认：

```bash
$ sh -c 'set -o pipefail'; echo $?
sh: 1: set: Illegal option -o pipefail
2
```

**退出码 2 + 零输出**就是它的特征签名。修法是在 job 上显式声明 shell，别指望默认值：

```yaml
defaults:
  run:
    shell: bash
```

顺带把 `DEVECO_SDK_HOME` 也写进 job `env`：`Prepare` 步骤要用它写 `local.properties` 的
`hwsdk.dir`，靠镜像 ENV 继承的话，一旦拿不到就会在 `set -u` 下静默中断。

**1. `local.properties` 必须现场生成。** 它被 `.gitignore` 排除，checkout 后不存在；
hvigor 靠 `hwsdk.dir` 找 SDK、flutter 靠 `flutter.sdk` 找自己，缺一个就构建失败。

**2. `flutter --version` 要跑两遍才能取到版本号。** 首次调用只负责下载 Dart SDK，
输出就一行 `Downloading Linux x64 Dart SDK...`，`head -1` 拿到的是这句话，不是版本号——我
第一版就是这么误判成「不是鸿蒙分支」的。正确写法是先把输出落到文件、判断里面有没有
`ohos`，没有再跑第二遍。

**3. 别用管道接 `head`。** `flutter --version | head -1` 在 `set -o pipefail` 下会因 SIGPIPE
退出 141 而失败。全程用重定向，`ver=$(head -n1 "$log")`。

### 对比过但没采用的三种写法

这几条来自社区里另外几套鸿蒙 CI，看着都合理，实测后否掉了。

**1. 从华为云镜像下 command-line-tools（免登录）**

`https://repo.huaweicloud.com/harmonyos/ohpm/<ver>/commandline-tools-linux-x64-<ver>.zip`
确实公开可下（实测 HTTP 200、`application/zip`、约 2 GB），既不用华为账号，也不用第三方
重打包。但这个仓库只有 `5.0.2 / 5.0.3 / 5.0.5 / 5.1.0`，最高 `5.1.0`（API 18），
而本项目 `compatibleSdkVersion: "26.0.0"`，装上去编不过。等它上了 26.x 再换，那时连
容器都可以不要。

**2. 预装 pnpm@8.13.1**

社区方案普遍加这一步，因为旧版 hvigorw 会自己 `npm install pnpm`。本镜像是 hvigor
6.26.9：实测容器内 `pnpm` 不存在、`~/.hvigor` 也没有，构建照样 43 秒通过，所以省掉。

**3. 浅克隆后手动 `git tag`**

社区方案用 `git clone --depth 1 -b <branch>`，浅克隆丢 tag，`flutter --version` 会报
`0.0.0-unknown` 导致 pub 求解失败，得手动补 tag。本项目直接 `-b <tag>` 克隆，tag 跟着
ref 一起下来，实测输出 `Flutter 3.47.7+ohos-0.0.1-pre`，不需要补。

**采纳的一条：放宽 ohpm 重试。** 本项目唯一的远程 ohpm 依赖是 devDependency
`@ohos/hypium`，镜像里没有缓存，每轮都要从 `ohpm.openharmony.cn` 拉，而镜像默认
`retry_times=1`、`fetch_timeout=60s`。`Harden ohpm for CI` 这一步把它放宽到 3 次 / 180 秒，
免得海外 runner 上一次抖动就整轮失败。

### 想改回自托管（35 秒出包）

托管 runner 每次都要拉 2.7 GB 镜像。若更看重速度：

1. 本机注册 runner 并打 `harmonyos` 标签：`./config.sh --url ... --token ... --labels harmonyos`
2. `runs-on` 改成 `[self-hosted, macOS, harmonyos]`，删掉 `container:` 与 `Cache flutter_flutter`
3. `Prepare` 里把 `FLUTTER_DIR` 指向 `$HOME/flutter_flutter`、`hwsdk.dir` 指向本机 SDK
   （可用 `vars.HARMONY_SDK_DIR` / `vars.HARMONY_FLUTTER_DIR` 覆盖）

实测同一台 Mac 上 `MODE=release` 完整构建 35 秒。代价是 runner 离线时 job 会排队拖住
`publish`，所以保留开关：仓库变量 `HARMONY_CI=false` 可跳过整个 job。

### 失败时看哪里

`Dump hvigor log on failure` 步骤会在构建失败时打印
`mobile/ohos/.hvigor/outputs/build-logs/build.log` 里的 ERROR 行和末尾 80 行。
flutter 本身只会吐 `exit code 255`，别被它误导（原因见上文「构建失败怎么定位」）。

产物是 **unsigned**：模拟器可直接装，真机需要先配签名，见 `docs/鸿蒙签名.md`。
