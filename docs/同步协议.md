# 客户端同步协议（pull / push）

> 面向原生客户端（Flutter / 移动端 / 桌面端）的增量同步接口。
> 相关工作台接口见 [API.md](API.md)，跨端总体方案见 [跨端客户端架构.md](跨端客户端架构.md)。

服务端把工作台数据当作一个可增量拉取的远程数据库：

- **pull**：按游标拉取自上次同步以来的变更快照，客户端不解析游标。
- **push**：批量提交离线操作，服务端按 `baseEtag` 做乐观并发控制，按 `opId` 幂等去重。
- **CalDAV 同源**：工作台、AI、CalDAV 客户端的所有写入都会进入同一份 `sync_logs`，因此三端看到同一份变更序列。

## 1. 认证与传输

| 项 | 约定 |
| --- | --- |
| 地址 | `GET /api/sync/pull`、`POST /api/sync/push`、`GET /api/sync/calendar` |
| 认证 | HTTP Basic Auth（CalDAV 账号密码） |
| CSRF | 不适用；接口只接受 Basic Auth，不接受会话 Cookie |
| 传输 | 生产环境必须 HTTPS |
| 请求体上限 | 4 MB；单批最多 200 个操作 |

```bash
curl -u admin:password 'https://dav.example.com/api/sync/pull?since=0&limit=500'
```

认证复用 CalDAV 的凭据缓存（5 分钟），密码修改后立即失效。

## 2. 实体与 ID

| `entity` | 说明 | 删除语义 |
| --- | --- | --- |
| `task` | 任务、笔记（`kind=NOTE`）、子任务 | 软删除（回收站），`deleted=true` |
| `list` | 清单（收集箱不可删除） | 物理删除，返回 tombstone |
| `section` | 看板列 | 物理删除，返回 tombstone |
| `folder` | 清单文件夹 | 物理删除，返回 tombstone |
| `filter` | 保存的筛选器 | 物理删除，返回 tombstone |

实体 ID 是**不透明字符串**：

- 新实体由客户端生成，推荐 ULID（26 字符 Crockford base32）；服务端原样保存，同一用户内唯一。
- 历史数据在升级时把原数字主键转成字符串（如 `"42"`），仍然有效。
- 客户端不要假设 ID 可排序或可解析；排序请使用 `order` 字段。

标签不是独立实体：标签集合内嵌在 `task.tags`，改名/删除标签请对任务做 `update`。

## 3. pull

```http
GET /api/sync/pull?since=<cursor>&limit=500&refresh=0&full=0
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `since` | `0` | 上次响应的 `cursor`；`0` 表示全量 |
| `limit` | `500` | 每页实体数，最大 1000 |
| `full` | `0` | `1` 等价于 `since=0` |
| `refresh` | `0` | `1` 先执行一次 CalDAV VTODO 对账，再返回 |

响应：

```json
{
  "cursor": "128",
  "hasMore": false,
  "serverTime": "2026-10-25T08:00:00Z",
  "tasks":   [ { "id": "01J...", "listId": "01J...", "title": "写协议", "etag": "v127", "version": 127, "deleted": false } ],
  "lists":   [ { "id": "01J...", "name": "工作", "etag": "v3", "version": 3 } ],
  "sections":[],
  "folders": [],
  "filters": [],
  "tombstones": [ { "entity": "list", "id": "01J...", "deletedAt": "2026-10-25T08:00:00Z" } ]
}
```

要点：

1. **游标单调递增**，属于用户级别的 `sync_logs.id`；客户端只保存、不解析。
2. 每页按「实体最后一次变更」折叠；同一实体在页内只出现一次，返回的是**当前快照**，不是中间状态。
3. `cursor` 推进到本页最后一条日志；`hasMore=true` 时立即用新 `cursor` 继续拉，直到 `false`。
4. `tasks` 包含回收站中的任务（`deleted=true`），方便客户端保留墓碑和恢复能力。
5. 物理删除的实体只出现在 `tombstones`；客户端应删除本地行。
6. `etag` 格式为 `v<seq>`，`version` 是同一个整数。它们是下一次 push 的并发基准。
7. 首次登录或本地库为空时直接 `since=0`；服务端会在升级时为历史数据补齐日志，因此全量拉取是完整快照。
8. 服务端在 pull/push 时最多每 10 秒执行一次 CalDAV 对账；需要立刻看到 CalDAV 客户端写入时使用 `refresh=1`。

### 实体字段

`task`：

```json
{
  "id": "01J...", "listId": "01J...", "parentId": "01J...", "sectionId": "01J...",
  "title": "写协议", "notes": "第一版", "notesFormat": "text", "kind": "TASK",
  "priority": 2, "start": "2026-10-25T09:00:00Z", "due": "2026-10-26T09:00:00Z",
  "allDay": false, "recurrence": "FREQ=WEEKLY;BYDAY=MO",
  "reminderOffsets": [30, 1440], "assignee": "alice",
  "completed": false, "completedAt": "", "pinned": false,
  "tags": ["sync"], "checklist": [{"id":"c1","title":"子步骤","done":false}],
  "order": 3, "deleted": false, "deletedAt": "",
  "createdAt": "2026-10-25T08:00:00Z", "modifiedAt": "2026-10-25T08:00:00Z",
  "etag": "v127", "version": 127
}
```

`list`：`id/name/color/kind/order/pinned/isInbox/folderId/createdAt/modifiedAt/etag/version`。
`section`：`id/listId/name/order/...`。`folder`：`id/name/order/...`。
`filter`：`id/name/color/conditions/order/pinned/...`，`conditions` 原样返回筛选器 JSON。

时间统一为 UTC RFC3339；`allDay=true` 时客户端按用户时区渲染日期。只发 `YYYY-MM-DD` 时服务端按部署默认时区（`Asia/Shanghai`）解析为当天零点，建议客户端始终发送带 `Z` 或偏移量的 RFC3339。

## 4. push

```http
POST /api/sync/push
Content-Type: application/json

{
  "deviceId": "device-a",
  "ops": [
    {
      "opId": "01JOP...",
      "entity": "task",
      "entityId": "01JTASK...",
      "action": "update",
      "baseEtag": "v127",
      "patch": { "title": "新标题", "completed": true }
    }
  ]
}
```

### 操作

| `action` | 语义 |
| --- | --- |
| `create` | 以 `entityId` 创建；已存在则 `conflict` |
| `update` | 字段级更新；`move` / `reorder` 是别名 |
| `delete` | `task` 进回收站；其他实体物理删除；重复删除返回 `ok`/`gone` |
| `restore` | 只对 `task`：从回收站恢复，清理完成状态并落到有效清单；已恢复时幂等返回 `ok` |
| `purge` | 只对 `task`：物理删除（活动/回收站均可），下发 tombstone；已物理删除返回 `gone` |
| `skip` | 只对重复任务：跳过当前实例并把 `due` 推进到下一次；无下一次时标记完成 |

`restore` / `purge` / `skip` 使用 `entityId` 定位，`patch` 可为空；同样受 `baseEtag` 冲突检查和 `opId` 幂等保护。

`patch` 只包含变更字段。**缺省字段保持不变**；显式 `null` 表示清空（日期、父任务、看板列、文件夹等）。
`create` 时 `entityId` 为空则由服务端生成并返回。

特殊字段：

- `listId` / `parentId` / `sectionId` / `folderId` 都使用对端实体的同步 ID。
- `reminderOffsets` 是「提前分钟数」数组，`0` 表示准时。
- `checklist` 是 `[{id,title,done}]`；`tags` 是字符串数组。
- `completed=true` 未带 `completedAt` 时由服务端补当前时间；`completed=false` 清空完成时间。
- 对 `recurrence` 非空且 `due` 存在的任务，`completed=true` **不会**把主任务标记完成，而是记录本次实例、写入 CalDAV `RECURRENCE-ID` 例外并把 `due` 推进到下一次；没有下一次时才标记完成。客户端会收到含新 `due` 的 `ok` 快照。
- `pinned` 由服务端维护置顶时间。
- 看板列删除默认把任务移回「未分组」；传 `patch.strategy="delete"` 会连同任务一起软删除，`targetSectionId` 可指定同清单内的目标列。
- 清空 `folderId` 表示把清单移出文件夹。

### 响应

```json
{
  "cursor": "140",
  "results": [
    { "opId": "01JOP...", "entityType": "task", "entityId": "01JTASK...",
      "status": "ok", "etag": "v139", "version": 139, "entity": { "...": "最新快照" } },
    { "opId": "01JOP2...", "entityType": "task", "entityId": "01JTASK2...",
      "status": "conflict", "etag": "v138", "version": 138, "entity": { "...": "服务端当前快照" },
      "error": { "code": "etag_mismatch", "message": "entity changed on the server" } }
  ]
}
```

| `status` | 客户端处理 |
| --- | --- |
| `ok` | 用返回的 `etag/version/entity` 覆盖本地，移除 outbox |
| `conflict` | 用 `entity` 做字段级或整行合并，再以新 `etag` 重试 |
| `gone` | 服务端已无该实体，彻底删除本地行 |
| `error` | 业务校验失败（`invalid_patch` 等），不要自动重试；展示或丢弃该操作 |

### 并发与幂等

1. `baseEtag` 省略时按「最后写入者赢」直接应用；提供时先比较服务端当前 `etag`。
2. 不一致立即返回 `conflict` 和最新快照，**不会写入**。
3. 服务端在单个进程内串行执行 push，缩小「检查-写入」窗口；Web 与 CalDAV 写入仍可能与 push 并发，因此客户端必须处理 `conflict`。
4. `opId` 按 `(用户, opId)` 去重，保留 7 天。重试同一 `opId` 返回第一次的结果，不会重复创建或重复删除。
5. 建议客户端为每个本地操作生成 ULID `opId`，并在收到结果前一直保留。

## 4.1 日历读取（只读）

```http
GET /api/sync/calendar?from=2026-10-01&to=2026-11-01
Authorization: Basic ...
```

返回工作台日历同源数据：

```json
{
  "calendars": [{ "id": 3, "name": "工作", "color": "#4772fa" }],
  "events": [
    { "id": "3:work/evt.ics:179...", "uid": "evt-1", "calendarId": 3,
      "calendarName": "工作", "color": "#4772fa", "summary": "周会",
      "start": "2026-10-26T02:00:00Z", "end": "2026-10-26T03:00:00Z",
      "allDay": false, "recurring": true, "reminders": [10],
      "location": "", "description": "", "readonly": false }
  ],
  "tasks": [
    { "id": 91, "syncId": "01JTASK...", "title": "写周报",
      "listName": "收集箱", "listColor": "#4772fa",
      "due": "2026-10-26T10:00:00Z", "allDay": false,
      "completed": false, "virtual": false, "occurrence": "2026-10-26T10:00:00Z" }
  ],
  "from": "2026-10-01T00:00:00Z",
  "to": "2026-11-01T00:00:00Z"
}
```

- `from`/`to` 支持 RFC3339 或 `YYYY-MM-DD`，最大跨度 120 天。
- `events` 已展开重复日历事件、节假日和 iCal 订阅，包含 CalDAV 绑定的所有 VEVENT 日历。
- `tasks` 包含范围内的普通任务和重复任务实例；`virtual=true` 表示只读展开实例，`syncId` 可映射本地任务。
- 此接口只读；任务修改仍走 `push`。
- 事件写入使用 Basic Auth 的 `POST /api/sync/events`、`PUT /api/sync/events`（body 带 `calendarId`/`href`）和 `DELETE /api/sync/events?calendarId=&href=`，只允许用户自己的 VEVENT 日历。`PUT` 带 `scope=single` + `recurrenceId` 时只改当前实例；`DELETE` 带 `recurrenceId` 时只删当前实例，服务端写入 `RECURRENCE-ID` 例外。
- iCal 订阅：`GET/POST /api/sync/subscriptions`、`DELETE /api/sync/subscriptions/{id}`；订阅事件由服务端抓取并在日历接口中返回。

## 4.2 习惯（移动端）

Basic Auth 习惯接口复用工作台逻辑：

```http
GET    /api/sync/habits
POST   /api/sync/habits
PATCH  /api/sync/habits/{id}
DELETE /api/sync/habits/{id}
POST   /api/sync/habits/{id}/checkin
GET    /api/sync/habits/{id}/detail?month=YYYY-MM
```

- `GET` 返回 `habits`、`sections`、`preferences`，以及最近 60 天的 `checkins`；`checkins` 是「习惯 ID → 打卡数组」的 map。
- `POST` / `PATCH` body 与工作台 Habit 字段一致（`name/color/goal/step/unit/frequency/...`）；`frequency` 是 JSON 字符串。
- `checkin` body `{"stamp": 20261025}`，无 `value` 时按 `step` 递增，达到 `goal` 后再次调用会撤销当天打卡。
- 打卡日期按服务端配置时区校验，不能早于习惯开始日期或晚于今天。

## 5. 与服务端其他写入路径的关系

`sync_logs` 由 SQLite 触发器维护，覆盖：

- 工作台 REST API（`/api/admin/tasks*`）
- AI 工具调用
- CalDAV VTODO 导入 / 对账（`internal/tasksync`）
- 直接修改任务表的维护脚本

触发器只记录**用户可见字段**的变化：`sync_pending`、`vtodo_uid/href/etag`、`notes_text`、`modified_at` 等簿记字段不会产生同步事件，避免每次 CalDAV 对账都唤醒客户端。

## 6. 保留与全量同步

| 数据 | 保留 |
| --- | --- |
| `sync_logs` | 90 天 |
| `sync_ops`（幂等结果） | 7 天 |

服务启动时清理一次，之后每小时最多清理一次。若客户端离线超过 90 天，`since` 可能早于最小可用日志；此时应重新 `since=0` 全量同步。当前协议不额外下发「需要全量」标志。

## 7. 当前范围与已知限制

- 已支持：`task`、`list`、`section`、`folder`、`filter`；标签通过任务字段同步。
- 习惯、专注、倒数日、笔记评论/附件、清单共享尚未纳入 pull/push。
- `recurrence` 以 RRULE 字符串同步；push 完成当前实例会推进到下一次并写 `RECURRENCE-ID`。`skip` 可跳过当前实例；顺延（postpone）、跨实例历史/例外列表的拉取仍未纳入移动端。
- 服务端不做字段级自动合并：冲突时返回服务端快照，由客户端合并后重试。
- `delete` 任务进入回收站而不是立即物理删除；`purge` 或清空垃圾桶会下发 tombstone。
- 附件（任务附件、评论附件）不在同步范围内，需单独按任务 ID 拉取。

## 8. curl 端到端示例

仓库提供 `scripts/sync-curl-demo.sh`，会模拟两个设备并发修改、冲突重试、幂等重放、CalDAV 写入和删除传播：

```bash
CALDAV_SYNC_PASS=password ./scripts/sync-curl-demo.sh http://127.0.0.1:5232 admin
```

完整输出示例：

```text
== 4. both devices edit the same revision: first wins, second conflicts
{"opId":"a-...","status":"ok","etag":"v4","title":"A 改的标题"}
{"opId":"b-...","status":"conflict","error":{"code":"etag_mismatch"},"serverTitle":"A 改的标题","serverEtag":"v4"}

== 7. a CalDAV client writes the same task collection
CalDAV PUT status=201
{"id":"01m5...","title":"来自 CalDAV 的任务 ...","etag":"v6"}
```
